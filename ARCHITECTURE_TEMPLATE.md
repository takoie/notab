# Architecture Template — Tauri v2 + Svelte 5 + Convex Desktop App

A reusable, domain-free skeleton for building a **cross-platform desktop app** with:

- **Desktop shell:** Tauri v2 (Rust) with a signed auto-updater
- **Frontend:** Svelte 5 (runes) + Vite + Tailwind CSS
- **Backend + database + realtime:** Convex (all-TypeScript, reactive, transactional)

This document describes only the *structure and wiring*. It contains no business
logic, no data model, and no feature descriptions — bring your own. Replace every
`myapp` / `MyApp` / `com.example.myapp` placeholder with your project's names.

---

## 1. Stack at a glance

| Layer | Technology | Role |
| --- | --- | --- |
| Desktop shell | Tauri v2 (`src-tauri/`, Rust) | Native window, packaging (NSIS/MSI), auto-update, OS integration |
| UI framework | Svelte 5 with runes (`$state`, `$derived`, `$effect`) | Reactive components, no router (conditional view switching) |
| Bundler / dev server | Vite 6 + `@sveltejs/vite-plugin-svelte` | HMR, build to static `dist/` |
| Styling | Tailwind CSS 3 + PostCSS + Autoprefixer | Utility classes, `darkMode: 'class'`, design tokens in `tailwind.config.js` |
| Icons | `lucide-svelte` | SVG icon components |
| Class helpers | `clsx` + `tailwind-merge` | Conditional / conflict-free class strings |
| Backend | Convex (`convex/`) | Queries, mutations, actions, schema, file storage, scheduling |
| Backend client | `convex/browser` `ConvexClient` | WebSocket subscription to reactive queries |
| Language | TypeScript everywhere (strict) | Shared types front + back |
| Process runner | `concurrently` | Runs Convex dev + frontend dev together |

### 3.4 Component organization

- One component per `.svelte` file under `src/lib/components/`.
- Group multi-file features in a subfolder (e.g. `components/onboarding/`).
- Pure helpers with no Svelte/Tauri imports live in `src/lib/utils/` so they stay
  trivially testable and reusable.
- `App.svelte` is the composition root: it instantiates every top-level query,
  holds global UI state, and decides which "view" is visible.

### 3.5 State & navigation (Svelte 5 runes)

No router. `App.svelte` keeps a string `activeView` in `$state` and renders
conditionally. Modals are booleans in `$state`. Derived values use `$derived`.
Side effects (persist to `localStorage`, subscriptions) use `$effect`.

```svelte
<script lang="ts">
  import Sidebar from '$lib/components/Sidebar.svelte';
  import HomeView from '$lib/components/HomeView.svelte';
  import DetailView from '$lib/components/DetailView.svelte';
  import { useQuery, useMutation } from '$lib/convex.svelte';
  import { api } from '../convex/_generated/api';

  // global UI state
  let activeView = $state<'home' | 'detail'>('home');
  let selectedId = $state<string | null>(null);
  let isModalOpen = $state(false);

  // reactive backend data — re-runs when the arg thunk's deps change
  const itemsQuery = useQuery(api.items.list);
  const itemQuery  = useQuery(api.items.get, () =>
    selectedId ? { id: selectedId } : undefined,   // undefined = skip query
  );

  const createItem = useMutation(api.items.create);

  const itemCount = $derived(itemsQuery.data?.length ?? 0);

  // client-side session persistence
  let userId = $state<string | null>(null);
  onMount(() => { userId = localStorage.getItem('myapp_user_id'); });
  $effect(() => {
    if (userId) localStorage.setItem('myapp_user_id', userId);
    else localStorage.removeItem('myapp_user_id');
  });
</script>

<Sidebar bind:activeView />
{#if activeView === 'home'}
  <HomeView items={itemsQuery.data} loading={itemsQuery.isLoading} />
{:else if activeView === 'detail'}
  <DetailView item={itemQuery.data} />
{/if}
```

**Session pattern:** there is no cookie/session server. After a successful
`loginOrRegister` mutation the returned `userId` is stored in `localStorage`
(`myapp_user_id`) and re-read on startup. Every backend call that needs identity
passes that id as an explicit argument, and the backend re-validates it
(see §4.4). Simple; not suitable for untrusted multi-tenant use without upgrading
to real auth (Convex Auth / OAuth).

## 4. Backend (Convex)

### 4.1 Golden rules

- **Always read `convex/_generated/ai/guidelines.md` first** — it overrides prior
  assumptions about Convex APIs.
- Use the **object form** for every function: `{ args: {...}, handler }`.
- Validate **all** args with `v.*` validators.
- `query` / `mutation` = transactional DB access, **no** `fetch`, no randomness at
  the top level. `action` = may call external APIs / use non-deterministic code,
  **no** direct DB access (calls queries/mutations via `ctx.runQuery/runMutation`).
- Prefix internal-only functions with `internalQuery/internalMutation/internalAction`
  and call them via `internal.*` (never exposed to the client `api.*`).

### 4.2 Function module pattern

```ts
// convex/items.ts
import { query, mutation, action } from './_generated/server';
import { v } from 'convex/values';
import { api } from './_generated/api';
import { requireUser } from './security';

export const list = query({
  args: {},
  handler: async (ctx) => {
    return await ctx.db.query('items').withIndex('by_created').order('desc').take(100);
  },
});

export const get = query({
  args: { id: v.id('items') },
  handler: async (ctx, args) => ctx.db.get(args.id),
});

export const create = mutation({
  args: { userId: v.id('users'), title: v.string() },
  handler: async (ctx, args) => {
    await requireUser(ctx, args.userId);
    const title = args.title.trim();
    if (title.length < 2) throw new Error('Title too short');
    return await ctx.db.insert('items', { title, createdAt: Date.now() });
  },
});

// External I/O goes in an action; batch requests to avoid rate limits.
export const importFromApi = action({
  args: { url: v.string() },
  handler: async (ctx, args) => {
    const res = await fetch(args.url, { headers: { Accept: 'application/json' } });
    if (!res.ok) throw new Error(`Upstream ${res.status}`);
    const data = await res.json();
    await ctx.runMutation(api.items.create, { userId: /* ... */, title: data.name });
  },
});

async function mapInBatches<T, R>(items: T[], size: number, work: (t: T) => Promise<R>) {
  const out: R[] = [];
  for (let i = 0; i < items.length; i += size)
    out.push(...(await Promise.all(items.slice(i, i + size).map(work))));
  return out;
}
```

### 4.3 Schema pattern (NOT a data model — just the shape)

`convex/schema.ts` defines tables and indexes. The example below is deliberately
generic; design your own tables.

```ts
// convex/schema.ts
import { defineSchema, defineTable } from 'convex/server';
import { v } from 'convex/values';

export default defineSchema({
  users: defineTable({
    username: v.string(),
    passwordHash: v.optional(v.string()),
    passwordSalt: v.optional(v.string()),
    role: v.string(),                 // e.g. "admin" | "user"
    createdAt: v.number(),
    lastActiveAt: v.optional(v.number()),
  })
    .index('by_username', ['username'])
    .index('by_role', ['role']),

  items: defineTable({
    title: v.string(),
    ownerId: v.optional(v.id('users')),
    createdAt: v.number(),
  })
    .index('by_created', ['createdAt'])
    .index('by_owner', ['ownerId']),
});
```

Conventions worth keeping:

- Timestamps are `v.number()` (`Date.now()`), not date objects.
- Every field you filter/sort by gets an index; name them `by_<field>`.
- Optional fields (`v.optional`) let you evolve the schema without migrations;
  when a shape stabilizes, tighten it and backfill with `@convex-dev/migrations`.
- Types flow to the frontend automatically via `_generated/dataModel` and
  `_generated/api` — never hand-write backend response types on the client.

### 4.4 Security / helper module pattern

Non-`function` helpers (no `query`/`mutation` wrapper) live in their own file and
are imported by function modules. Keep three responsibilities separate:

```ts
// convex/security.ts
import { MutationCtx, QueryCtx } from './_generated/server';
import { Id } from './_generated/dataModel';

// 1. Password hashing — PBKDF2-SHA256 via Web Crypto (works in Convex runtime)
export async function hashPassword(password: string, saltHex?: string) {
  const enc = new TextEncoder();
  const salt = saltHex ? hexToBytes(saltHex) : crypto.getRandomValues(new Uint8Array(16));
  const keyMaterial = await crypto.subtle.importKey('raw', enc.encode(password),
    { name: 'PBKDF2' }, false, ['deriveBits']);
  const bits = await crypto.subtle.deriveBits(
    { name: 'PBKDF2', salt: salt as BufferSource, iterations: 100_000, hash: 'SHA-256' },
    keyMaterial, 256);
  return { hash: bytesToHex(new Uint8Array(bits)), salt: bytesToHex(salt) };
}
export async function verifyPassword(pw: string, storedHash: string, storedSalt: string) {
  const { hash } = await hashPassword(pw, storedSalt);
  return hash === storedHash;
}

// 2. Output sanitizers — strip secrets before returning to the client
export function sanitizeUser<T extends Record<string, any>>(u: T | null): T | null {
  if (!u) return null;
  const { password, passwordHash, passwordSalt, ...safe } = u;
  return safe as T;
}

// 3. Authorization guards — call at the top of every protected handler
export async function requireUser(ctx: QueryCtx | MutationCtx, userId?: Id<'users'> | string | null) {
  if (!userId) throw new Error('Unauthorized: user id required');
  const user = await ctx.db.get(userId as Id<'users'>);
  if (!user) throw new Error('Unauthorized: user not found');
  return user;
}
export async function requireAdmin(ctx: QueryCtx | MutationCtx, userId?: Id<'users'> | string | null) {
  const user = await requireUser(ctx, userId);
  if (user.role !== 'admin') throw new Error('Forbidden: admin only');
  return user;
}
```

Helpers `hexToBytes` / `bytesToHex` are small local functions in the same file.

### 4.5 Pure helper modules

Logic that transforms data but does no I/O goes in its own module (e.g.
`convex/<feature>Helpers.ts`) with plain exported functions. Benefits: unit-test
without a Convex context, reuse from both `query` and `action`, keep handlers thin.

### 4.6 File storage

Upload flow: a `mutation` returns `await ctx.storage.generateUploadUrl()`; the
client `PUT`s the file to that URL and gets back a `storageId`; a second
`mutation` calls `ctx.storage.getUrl(storageId)` and persists the URL on a
document. Add `https://*.convex.cloud` to `img-src` / `media-src` in the CSP.

### 4.7 Extension points (not used in the base skeleton)

- **Scheduling:** `ctx.scheduler.runAfter(ms, internal.x.y, args)` for one-shot jobs.
- **Cron jobs:** `convex/crons.ts` with `cronJobs()` for recurring work.
- **HTTP endpoints:** `convex/http.ts` with `httpRouter()` for webhooks (served on
  `*.convex.site` — already in the CSP `connect-src`).
- **Components:** `@convex-dev/*` drop-ins (auth, rate limiting, search, agent…).

## 5. Frontend ↔ Convex wiring

### 5.1 Client singleton + reactive hooks

`src/lib/convex.svelte.ts` is the single integration point. It creates one
`ConvexClient` and exposes runes-based wrappers.

```ts
// src/lib/convex.svelte.ts
import { ConvexClient } from 'convex/browser';
import type { FunctionReference, FunctionArgs, FunctionReturnType } from 'convex/server';

export const convexUrl: string =
  (import.meta as any).env?.VITE_CONVEX_URL ?? 'http://127.0.0.1:3210';

export const convexClient = new ConvexClient(convexUrl);

/** Reactive query: subscribes via WebSocket, re-subscribes when args change. */
export function useQuery<Q extends FunctionReference<'query'>>(
  query: Q,
  args: () => FunctionArgs<Q> | undefined = () => ({} as FunctionArgs<Q>),
) {
  let data = $state<FunctionReturnType<Q> | undefined>(undefined);
  let isLoading = $state(true);
  let error = $state<Error | null>(null);

  $effect(() => {
    const a = args();
    if (a === undefined) { data = undefined; isLoading = false; return; } // skip
    isLoading = true; error = null;
    const unsub = convexClient.onUpdate(query, a,
      (r) => { data = r; isLoading = false; error = null; },
      (e) => { error = e; isLoading = false; });
    return () => unsub();
  });

  return {
    get data() { return data; },
    get isLoading() { return isLoading; },
    get error() { return error; },
  };
}

export function useMutation<M extends FunctionReference<'mutation'>>(mutation: M) {
  let isPending = $state(false);
  let error = $state<Error | null>(null);
  async function mutate(args: FunctionArgs<M>): Promise<FunctionReturnType<M>> {
    isPending = true; error = null;
    try { return await convexClient.mutation(mutation, args); }
    catch (e: any) { error = e instanceof Error ? e : new Error(String(e)); throw error; }
    finally { isPending = false; }
  }
  return { mutate, get isPending() { return isPending; }, get error() { return error; } };
}

export function useAction<A extends FunctionReference<'action'>>(action: A) {
  let isPending = $state(false);
  let error = $state<Error | null>(null);
  async function execute(args: FunctionArgs<A>): Promise<FunctionReturnType<A>> {
    isPending = true; error = null;
    try { return await convexClient.action(action, args); }
    catch (e: any) { error = e instanceof Error ? e : new Error(String(e)); throw error; }
    finally { isPending = false; }
  }
  return { execute, get isPending() { return isPending; }, get error() { return error; } };
}
```

### 5.2 Typed function references

Import `api` from `../convex/_generated/api` and reference functions as
`api.<module>.<export>` (e.g. `api.items.list`). Args and return types are
inferred end-to-end. Never import from `convex/` source directly on the client.

### 5.3 Loading & skip semantics

- The arg thunk returning `undefined` means "don't run this query yet" — use it
  for queries that depend on a not-yet-known id.
- `isLoading` is `true` until the first result arrives; after that the query
  stays live and pushes updates automatically (no polling, no refetch calls).

### 5.4 Required CSP entries for Convex

In **both** `index.html` `<meta>` and `src-tauri/tauri.conf.json` `app.security.csp`:

```
connect-src ... https://*.convex.cloud wss://*.convex.cloud https://*.convex.site wss://*.convex.site
img-src     ... https://*.convex.cloud https://*.convex.site
media-src   ... https://*.convex.cloud https://*.convex.site
```

(`*.convex.cloud` = function calls + WS; `*.convex.site` = HTTP actions + file
storage URLs.)

#[tauri::command]

    // stream download with reqwest, emit "update-progress" events, ShellExecute, exit(0)

#[cfg_attr(mobile, tauri::mobile_entry_point)]

    tauri::Builder::default()
        .plugin(tauri_plugin_opener::init())
        .plugin(tauri_plugin_updater::Builder::new().build())
        .plugin(tauri_plugin_process::init())
        .setup(|app| {
            // optional: size the window relative to the active monitor, then center
            Ok(())
        })
        .invoke_handler(tauri::generate_handler![greet, download_and_launch_installer])
        .run(tauri::generate_context!())
        .expect("error while running tauri application");
}
```

# src-tauri/Cargo.toml (deps)
[dependencies]
tauri = { version = "2", features = [] }
tauri-plugin-opener  = "2"
tauri-plugin-updater = "2"

serde_json = "1"

```

### 6.3 Permissions (`src-tauri/capabilities/default.json`)

Least-privilege allowlist for the `main` window. Start minimal and add as needed:

```jsonc
{
  "$schema": "../gen/schemas/desktop-schema.json",
  "identifier": "default",
  "windows": ["main"],
  "permissions": [
    "core:default",
    "core:window:allow-start-dragging",
    "core:window:allow-minimize",
    "core:window:allow-toggle-maximize",
    "core:window:allow-close",
    "opener:allow-open-url",
    "updater:allow-check",
    "updater:allow-download-and-install",
    "process:allow-restart"
  ]
}
```

Frameless window (`decorations: false`) means the frontend renders its own title
bar and calls `getCurrentWindow().minimize()` / `.toggleMaximize()` / `.close()`
and `startDragging()` on a drag region — hence the `core:window:*` grants.

### 6.4 Auto-updater

1. Generate a signing keypair once (`npx tauri signer generate`); commit the
   **public** key into `tauri.conf.json`, keep the **private** key out of git.
2. `createUpdaterArtifacts: true` makes the build emit a `.sig` next to the
   installer.
3. `scripts/build-release.cjs` writes `latest.json` (see §8) and you upload
   installer + `latest.json` to the GitHub release the `endpoints` URL points at.
4. On launch the frontend calls the updater plugin; on "update available" it
   downloads + installs and restarts via `tauri-plugin-process`.

| File | Committed? | Purpose |
| --- | --- | --- |
| `.env.example` | yes | Documents the variables; no real values |
| `.env.local` | no (gitignored) | Written by `npx convex dev`: `CONVEX_DEPLOYMENT`, `VITE_CONVEX_URL`, `VITE_CONVEX_SITE_URL` |

read via `process.env` inside Convex functions — never bundled into the frontend.

## 9. Release & versioning flow

### 9.1 Version bump

The version currently lives in several places — keep them in lockstep (or, better,
generate the frontend-visible ones from `package.json` at build time):

- `package.json` → `version`
- `src-tauri/tauri.conf.json` → `version`
- `src-tauri/Cargo.toml` → `version`
- any hard-coded `currentVersion` in the UI (e.g. an "About" component / update modal)

### 9.2 Signed build

```bash
npm run build:exe
```

`scripts/build-release.cjs` does:

1. `npm run build` — frontend → `dist/`.
2. Read the private signing key from a local file (path checked, not committed),
   set `TAURI_SIGNING_PRIVATE_KEY` + `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`, run
   `npx tauri build`. Produces (Windows): `*_x64-setup.exe` (NSIS),
   `*_x64_en-US.msi` (MSI), and `*_x64-setup.exe.sig`.
3. Write `latest.json` at the repo root:

```jsonc
{
  "version": "v0.1.0",
  "notes": "MyApp v0.1.0",
  "pub_date": "2026-01-01T00:00:00.000Z",
  "platforms": {
    "windows-x86_64": {
      "signature": "<contents of the .sig file>",
      "url": "https://github.com/<org>/<repo>/releases/download/v0.1.0/MyApp_0.1.0_x64-setup.exe"
    }
  }
}
```

### 9.3 Publish

```bash
git commit -am "release: v0.1.0"
git tag -a v0.1.0 -m "MyApp v0.1.0"
git push origin main --tags
gh release create v0.1.0 \
  "src-tauri/target/release/bundle/nsis/MyApp_0.1.0_x64-setup.exe" \
  "src-tauri/target/release/bundle/msi/MyApp_0.1.0_x64_en-US.msi" \
  "latest.json" \
  --title "MyApp v0.1.0" --notes "Changelog…"
```

The updater `endpoints` URL resolves to the `latest.json` of the newest release,
so shipping an update = publishing a new release with these three assets.

### 9.4 Deploying the backend

Convex deploys independently of the desktop app:

```bash
npx convex deploy            # push schema + functions to the prod deployment
```

Run this whenever `convex/` changes; the installed desktop clients pick up the
new backend immediately (same `VITE_CONVEX_URL`). Coordinate schema changes with
`@convex-dev/migrations` when data must be backfilled.

## 11. Bootstrapping a new app from this skeleton

1. `npm create vite@latest myapp -- --template svelte-ts` (or copy this layout).
2. Add Tailwind: `npm i -D tailwindcss postcss autoprefixer` + the three config
   files; put `@tailwind` directives in `src/app.css`.
3. `npm i convex && npx convex dev` — creates the deployment, `convex/`,
   `_generated/`, and `.env.local`. Read `convex/_generated/ai/guidelines.md`.
4. Create `src/lib/convex.svelte.ts` (§5.1) and wire `main.ts` → `App.svelte`.
5. `npm i -D @tauri-apps/cli && npx tauri init` — point `frontendDist` at
   `../dist`, `devUrl` at `http://localhost:1420`, set `identifier`.
6. Add the Convex CSP entries to **both** `index.html` and `tauri.conf.json` (§5.4).
7. Add updater: `npx tauri add updater`, `npx tauri signer generate`, fill
   `plugins.updater` in `tauri.conf.json`, copy `scripts/build-release.cjs`.
8. Design your `convex/schema.ts` and `security.ts`, then build features as
   `convex/<feature>.ts` + `src/lib/components/*`.
9. `npm run dev:desktop` to develop; `npm run build:exe` + `gh release create` to
   ship.
